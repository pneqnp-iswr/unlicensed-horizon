# Independent resource feasibility: Horizon 26.3

Verified against upstream Horizon source / docs on 2026-10-30. This is a **technical dependency note**, not a claim that standalone assets have been implemented.

## Code facts

- The Rust client accepts `--name` without an authenticated session (`crates/horizon-client/src/game.rs`, `Options::read`); the signed account is optional and required for online-mode servers.
- The very first missing-resource test in the client checks the `horizon-resources.json` marker (also in game.rs).
- Horizon then loads prepared world data and resources from the root. The generated data includes registries, commands, block states, recipes, biome and worldgen data, item components, model and blockstate assets.
- Most of this is generated by `horizon-prepare` using an owner's Minecraft Java 26.3 client/server data, JDK 25 and upstream's Java data generators. A texture pack only replaces some render inputs; it does not create equivalent gameplay registries or behavior.
- Worlds and options files reside relative to `std::env::current_dir()`, *not* automatically below `HORIZON_HOME`. Fixed in v0.3.

## Possible engineering route for a genuinely independent open-content game

1. Record exact resource loader schemas and mandatory files from the MIT-licensed Horizon Rust source. Distinguish proprietary derived data from independently authored content.
2. Generate a **minimal original** registry, worldgen and command dataset for a tiny test environment, using authored values (not copying Mojang data). A generated marker alone is not sufficient.
3. Create an openly licensed pack of original textures, models, sounds, language strings and GUI textures, linked to the generated registry.
4. Run staged boot tests (resource load, title, test terrain, singleplayer, save/reload). Amend the Horizon loader where its assumptions force the exact vanilla format.
5. Keep a license/provenance manifest for every input. Only distribute artifacts whose rights permit redistribution.

This path may evolve into a **distinct open-content voxel game built on the Horizon engine**. It is not a quick launcher switch and is not yet implemented.

## v0.4 verified early-loader contract (upstream, 2026-10-30)

- `crates/horizon-client-render/src/assets.rs`: `Assets::load` first requires `horizon-resources.json` with integer `data_version = 5023`, then `facts.json` and `block-tags.json`. The latter contains a JSON object with **JSON strings** as tag file values, not nested JSON objects. All 3 named heightmap/fluid tag entries must resolve. It also requires 6 vanilla-named material states for internal test scenes.
- `crates/horizon-world/src/registry/facts.rs`: `facts.json.states` rows use the form `[name, air_boolean, fluid_boolean, description, state_descriptor]`. `defaults` maps each state name to its default state index. A 7-state original schema example has been generated in `examples/original-resource-lab/`.
- `crates/horizon-core/src/version.rs`: `DATA_VERSION=5023` for 26.3. This is version pinned.
- `crates/horizon-client/src/game.rs`: subsequent startup needs `block-behaviours.json`, `Biomes::load`, `Environment::load`, `BlockFacts`, `PackResources` and more; marker-only fake files are insufficient.
- `crates/horizon-client-render/src/biome.rs`: colormap files for grass, foliage, dry_foliage and JSON biome directory `data/minecraft/worldgen/biome`.
- `docs/native-client.md`: client supports `--render-distance` 2..128, correcting the old v0.3 value.

**Independent lab output:** procedural tiles, color maps, 7 entries in a well-formed block registry, three JSON-encoded tag definitions, one biome, basic models, explicit "not playable" provenance. This should be treated as a *schema and asset authoring experiment*, not a bootable resource tree; no Rust loader integration test has run. `doctor` refuses this lab deliberately.

## v0.5: What the independent lab actually validates

Code cross-checked on 2026-10-30 with:

- `crates/horizon-client-render/src/assets.rs` (`Assets::load` core manifest, facts, three required block tags)
- `crates/horizon-world/src/registry/facts.rs` (five-field rows and default indices, compound `{id, properties}` form)
- `crates/horizon-client-render/src/models.rs` (16 gallery placements, 12 nontrivial additional block names)
- `crates/horizon-client-render/src/models/catalog.rs` (`model-states.json`, schema, state ordering, blockstate model references)
- `crates/horizon-world/src/worldgen/tags.rs` (nested JSON strings containing `values`, identifier resolution)
- `crates/horizon-client-render/src/biome.rs` (256x256 colormaps and biome directory)

The new open lab supplies 19 registry states, 3 tag bundles, 18 model bindings, 36 decoded PNGs. Its validator cross-checks the *supported subset*, and the archive includes an example for reproducibility. It has **not** been run through the Rust crates. The actual Rust `load_resources` runs UI, `Assets::load`, `Assets::reload`, `BlockFacts`, `Biomes`, `Environment`, lighting, `PackResources`, collision/motion, more world and game CPU data; all these must be handled in a fully independent playable adaptation. Merely extending the minimal registry does not make Horizon playable.

The Go subset checker intentionally does not claim precise emulation of weighted model selection, tag conflict order, binary NBT or full resource-pack semantics. As new schemas are added, compare them to upstream and validate against Rust. The project explicitly rejects these experimental files for normal Play even if the extra lab marker is removed.

## v0.6: a real Horizon probe is now possible (not yet executed here)

The current upstream `game.rs` exposes `--frames`, `--timeout-seconds`, `--test-terrain`, `--offscreen`, and `--smoke-report`. Its `synchronous_startup` selects the full synchronous loader path for frame-limited smoke tests; `load_resources` invokes `UiResources`, `Assets::load`, `RenderAssets::load`, then behaviour/facts/biomes/environment, lighting and pack tables, collision/motion, and world-rest tables. This is why faking a resource-marker success never equates to a boot.

`environment.rs::Environment::load_dimension` directly reads the files `data/minecraft/timeline/day.json` and `data/minecraft/dimension_type/overworld.json`. The v3 lab now authors both, independently, with a minimal day curve and original sky attributes. Its Go contract tests validate the small new subset (and detect broken timeline periods); this is not a Rust deserialization or renderer test.

`lab-probe` prevents user-world contamination by copying every inventoried file to a new scratch root and isolating the client home/environment. On a PC holding an actual Horizon binary, it records the *first real loader failure*. The exit status and smoke-file presence are evidence of an attempted test, **not** proof of a playable game. A user needs to run it on a GPU-equipped Windows system for first integration results.
